- 원안: [PLAN.md](../../PLAN.md)의 0단계/P5를 바탕으로 보존·정확성 검사를 추가한다.
- 초기 자료: [실행·재현 결과](../results/2026-10-06-initial/README.md)

## 목적과 범위

같은 입력에 대해 레거시의 품질, 정보 손실, 실행 성능을 다시 측정할 수 있게 만든다.
첫 대상은 저장소의 두 예제다. 원안의 멀티 AZ + ALB → EKS/ECS → Aurora는 현재 별도 입력 파일이 없으므로,
1단계에서 작은 합성 입력으로 만들고 실제 사용자 그림과 구분한다.
이번 계획은 측정 도구·입력·결과까지다. ELK 설치, 제품 로직 수정, UI 개편, AWS 실제 호출은 포함하지 않는다.

## 1. 측정 정의와 입력 고정

1. 두 예제의 파일 hash, 셀/선/그룹 수, 원본 ID와 geometry, 끝점·경로 표현을 기록한다.
2. 실제 입력이 제공하는 것과 누락한 것을 조사한다. 등록된 JSON에서 생성한 그림만으로 평가하지 않는다.
3. 보존 검사용으로 수동 위치·메모·미등록 AWS 아이콘·동일 라벨·연속 명령 사례를 고정한다.
   예제에 없는 사례는 작은 합성 입력임을 표시한다.
4. 조율자가 측정 예시를 준비한 뒤 사용자에게 익명화한 정답 그림 3개를 요청한다. 제공 전에는 미확보로 기록한다.
   실제 그림이 추가되면 버전과 hash를 기록한다. 합성 입력을 사용자 정답으로 취급하지 않는다.
5. 원본과 레거시 정렬 결과를 각각 보관한다. 서비스 추가도 별도로 비교한다.
6. 커스텀 style 키를 넣고 draw.io 저장→열기 왕복 후 XML에서 보존 여부를 확인한다.
   이는 원안 P2의 사전 확인이며 의도 스키마 구현은 이번 범위에 포함하지 않는다.

### 지표 초안

| 구분 | 지표 | 정의·주의점 |
|---|---|---|
| 보존 | 셀/선/ID/타입/소속 손실·변경 수 | 의도한 추가·삭제를 제외하고 원본과 비교. 셀 개수만 같다고 보존 성공이 아니다. |
| 보존 | 기존 geometry·스타일 변경 수 | 서비스 추가에서 기존 위치·크기·스타일 보존을 검사. 명시적 정렬에서는 좌표 변경을 손실로 세지 않는다. |
| 정확성 | 명령 결과·오류·롤백 정합성 | 단일/연속 명령의 실제 결과를 기대 결과와 비교. 성공 메시지만 세지 않는다. |
| 배치 | 노드 겹침 | 절대 좌표로 환산. 의도한 부모 컨테이너와 자식의 포함 관계는 제외. 라벨 겹침은 별도 측정 가능 여부를 표시. |
| 배치 | 선 교차·다른 노드 관통 | 실제 선 경로가 필요. 공통 끝점은 교차로 세지 않고 source/target 노드는 관통 대상에서 제외. 겹친 선 처리도 정의한다. |
| 배치 | 주 흐름 역방향 선 | 주 흐름과 방향을 입력에 명시. 자동 추정과 명시 정보를 섞지 않는다. |
| 배치 | AZ 대칭·면적 | 비교할 AZ의 대응 노드를 명시. 면적은 전체 경계 상자. 정답이 없으면 area ratio 대신 원래 면적/절대 면적을 기록. |
| 실행 | 시간·실패 수·번들 크기 | 같은 환경·입력·옵션과 반복 횟수를 기록. 테스트/빌드 결과는 배치 품질과 분리. |

**주의:** 레거시 XML에는 draw.io가 화면에서 계산한 경로가 없을 수 있다.
waypoint/끝점이 없는 선을 중심점 직선으로 가정해 “실제 교차 수”를 만들지 않는다.
그 지표는 `미측정`과 이유, 전체 선 중 측정 가능한 수를 적고 필요하면 실제 렌더링 경로를 얻는 별도 절차를 만든다.
서비스나 선이 사라진 결과를 0점의 좋은 결과로 평가하지 않는다.

검증: 각 지표의 단위·계산 범위·제외 조건·미측정 조건·좋아지는 방향과 입력 manifest가 있다.

## 2. 최소 측정기와 기준선

1. 기존 DOM/XML 처리와 Vitest를 재사용하고 불필요한 의존성은 추가하지 않는다.
2. 먼저 측정기가 겹침/분리, 부모 상대좌표, 데이터 손실을 구분하는 작은 검사를 만든다.
   실제 경로 추출 전인 교차/공통 끝점 검사는 B007로 남기고 이번 실행에서 교차 값을 채우지 않는다.
3. 1단계에서 실제 계산 가능한 지표부터 구현한다. 나머지는 한계와 다음 검증을 기록한다.
4. 출력은 입력별 표와 원시 JSON 정도로 제한한다. 대시보드는 만들지 않는다.
5. 원본 → 레거시 계층 정렬/좌→우 정렬/서비스 추가를 실행해 결과 XML과 측정값을 보관한다.
6. `npm test`, `npm run build`와 측정기 검사를 실행한다.

결과 위치: `development/results/<날짜>-baseline/`.
기록: 코드 SHA와 dirty 변경, 환경, 입력 hash, 도구 버전, 명령·옵션·반복 횟수,
원시 결과, 측정 가능한 수/전체 수, 미측정 이유, 실패 결과도 포함한다.

검증: 같은 입력으로 재실행 가능하고 구조·보존·가능한 배치 지표의 기준선 표가 있다.
실행시간은 분포를 적고 환경이 다른 숫자를 직접 비교하지 않는다.

## 3. 시각 평가와 다음 계획

2026-10-07 [사용자 지시](../discussions/2026-10-07-kb-priority.md)에 따라 KB자산운용을 최우선 필수 통과 대상으로 삼는다.
실제 파일 6개 중 KB는 두 파일·7페이지다. 우선 둘 다 검증하며 다른 그림의 개선으로 KB 실패를 상쇄하지 않는다.
기존 실행기는 단일 페이지 입력만 지원하므로 KB의 페이지 ID·이름·순서를 유지하는 기준선 실행을 먼저 준비한다.
페이지별 측정과 파일 전체의 페이지 보존 검사를 구분하고, 기존 결과를 덮어쓰지 않는다.
서비스·그룹뿐 아니라 표·메모·일반 도형, 참조가 없는 선과 경로도 검증에 포함한다.
현재 입력은 실제 예시로 확보한 상태이며 사용자 정답 판정·공유용 익명화까지 완료했다고 취급하지 않는다.

원본과 레거시 결과를 같은 화면 배율·범위로 비교하고 사람이 판단한 문제를 기록한다.
“보기 좋다”와 자동 지표를 구분한다. 사용자 확인을 대신 했다고 쓰지 않는다.
기준선 분포와 관측 한계를 보고 다음 단계의 개선 목표·허용치·중단 기준을 결정한다.
그 뒤 ELK 실험 또는 데이터/명령 흐름 재설계 계획을 작성한다.
ELK 실험을 선택하면 원안의 “지표와 눈 판정 둘 다 개선이 없으면 접는다”를 중단 기준으로 이어간다.
사용자 시각 판정이 아직 없으면 미판정으로 남기고 자동으로 개선을 선언하지 않는다.

## 완료와 중단 기준

- 완료: 버전이 고정된 입력, 재실행 명령, 검증된 측정기, 지표별 기준선/미측정 한계,
  시각 자료와 평가 상태, 다음 개발을 위한 판단 근거가 연결돼 있다.
- 선 경로나 정답 입력이 없어 일부 지표가 불가능하면 가능한 측정은 계속한다.
  불가능한 값은 완료값으로 꾸미지 않고 후속 검증·담당을 명시한다.
- 데이터 손실이 보이면 그 결과를 남기되 배치 품질 향상의 근거로 쓰지 않는다.
- 측정기 오류나 비교 조건 변경이 드러나면 수정을 먼저 하고, 이전 결과에 무효 이유와 후속 결과를 연결한다.
