# 0001 — 개발 기록과 기준선부터 시작한다

- 날짜: 2026-10-06
- 상태: 합의
- 근거: [사용자 논의](../discussions/2026-10-06-restart.md), [초기 검토 결과](../results/2026-10-06-initial/README.md)
- 계획: [0001 — 기준선](../plans/0001-baseline.md)

## 선택과 이유

개발 전에 기준선을 측정하고, 판단 과정을 저장소의 `development/`에 연결해 남긴다.
사용자가 명시적으로 요청한 작업 방식이며, 현재 테스트 통과만으로 실제 편집 품질을 설명할 수 없기 때문이다.
레이아웃 품질과 함께 원본 보존·명령 정확성을 측정한다. 데이터 손실이 있는 결과의 배치 점수 향상은 채택 근거로 쓰지 않는다.

기존 구현의 구조는 유지 의무가 없다. 다만 기준선 측정 전에 제품 동작을 바꾸면 비교 대상이 사라지므로,
현재 코드 버전·입력·재현 방법을 먼저 고정한다. 전면 재작성과 ELK 채택은 아직 미결이다.

## 고려한 대안

- 바로 ELK 교체: 비교 근거가 없고 배치와 데이터 보존의 문제를 섞어서 평가하게 된다.
- 바로 전면 재작성: 가능하지만 어떤 품질을 달성해야 하는지 먼저 정의해야 한다.
- 대화에만 기록: 세션이 사라지면 결정 이유와 후속 계획의 연결을 찾기 어렵다.

## 영향

다음 개발 항목은 측정 정의와 기준선이다. 루트 `PLAN.md`는 원안으로 보존한다.
현재 계획은 `development/plans/`에서 관리하고 백로그를 진입점으로 사용한다.
중요한 결정을 바꾸면 새 결정과 근거를 연결한다. 원래 측정 결과를 덮지 않는다.
